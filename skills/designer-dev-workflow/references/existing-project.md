# 补充路径：已有项目与局部变更

仅在接手已有项目或执行局部改动时读取。默认产品主线是 0→1 设计系统与业务页面建设；已有项目支持保留，不要求重建设计系统或 Gallery。

先核验真实代码、技术栈、命令、相关设计规范与资产。已有 Adapter 是索引，核验相关字段；差异以源码和配置为准。现有 token 工具链、组件库和 Storybook/文档站优先复用。局部需求只修改受影响资产并同步现有 Gallery；没有 Gallery 时，不因一个小修改强制扩展范围，按用户确认的建设范围处理。

## 变更分诊

| 路径 | 类型 | 原则 |
|---|---|---|
| A | token / 设计变量 | 修改真实源 token，避免业务代码硬编码 |
| B | 已有组件变更 | 先读规范与实现，评估共享影响 |
| C | 新增通用组件 | 先证明无法复用，再新增并登记 |
| D | 新增页面 / 路由 | 实现页面、接路由、补页面规范 |
| E | 新增业务流程 | 复用组件，补齐数据与状态链路 |
| F | 组合需求 | 拆成组件、页面、业务分步执行 |

按主流程的 Spec、源码交付和验证要求完成确认范围。高影响范围变化回写 Spec 并确认；不把局部改动扩成全项目规则巡检。

## 按需扫描与模板

CLI 可用时运行 `design-workflow scan <项目目录> --json`；也可从主 Skill 目录运行 `node scripts/scan-project.mjs <项目目录>`。没有 Node.js 时使用宿主文件搜索，不为扫描要求安装环境。

扫描读取 `.design-workflow/config.json` 的目录配置。`init` 只创建缺失模板并刷新 Adapter，不自动实现页面或 Gallery。`doctor` 的 healthy/structureReady 仅说明结构诊断，不能替代源码接入、页面渲染或业务验证。
