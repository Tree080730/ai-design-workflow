# 架构说明

当前定位是优先面向 0→1 设计系统构建与业务页面搭建的宿主 Design Harness：Skills 与项目设计资产是核心；CLI 是可选确定性工具。宿主 Agent 提供模型、执行循环、权限、文件/命令/浏览器和会话能力。本项目提供本地设计选择 GUI，不另建 Agent 运行时或模型 API。GUI 将选择写入项目设计依据；Skills 读取并推进实现，当前通过共享文件与交接指令接入宿主。

接入层只负责把同一份 Skills 安装到宿主发现目录，并在项目指令中增加短入口。具体安装与能力边界见 [宿主接入](host-integration.md)。0→1 默认交付契约与检查器随 Skill 分发，复用现有 task 证据引擎；token 导出、资产清单及独立 task 管理仍为按需增强。

## 1. Harness 与 Skills 的职责

| 层 | 解决的问题 | 典型输入 | 主要输出 |
|---|---|---|---|
| Harness | 哪些操作必须确定、可重复、可测试 | 代码仓库、CLI 参数 | 扫描结果、初始化文件、检查与诊断 |
| Workflow | 一次需求应按什么顺序完成 | 用户需求、代码仓库 | Adapter、方案 spec、实现、检查报告、交付记录 |
| Design System | 将确认约束转成可复用的运行资产 | 产品需求、参考资料与确认约束 | tokens/样式与组件源码、Gallery、布局/交互规范 |
| Proposal | 没有明确设计稿时如何选择方向 | 需求、设计系统、现有组件 | 方案摘要、选中方案预览、决策记录 |

`rules-governance` 位于检查层：它验证前三层产物是否保持一致，但不参与普通需求的方案决策。

```text
CLI Harness
├─ scan：只读识别项目
├─ init：非覆盖式创建模板与索引
├─ check：确定性规则检查
├─ doctor：环境与状态诊断
└─ delivery：默认范围、源码接入与验证证据判定（也随 Skill 分发）
        ↓ 提供事实与工具
Skills
├─ Workflow：编排
├─ Design System：设计约束
├─ Proposal：方案决策
└─ Rules Governance：语义审查
```

## 2. Project Adapter 的定位

Adapter 不是事实来源，而是项目事实的结构化索引：

- 事实来源：源码、配置、设计系统、规则文档和可执行命令。
- Adapter：记录这些事实在哪里、如何使用、最近一次核验时间。
- 主流程：先读 Adapter，再对关键字段做轻量核验；发现漂移时更新 Adapter。

它的价值不是让 Agent “第一次才能读懂项目”，而是减少每次重复扫描、降低遗漏，并让不同 Agent 使用同一套项目映射。

## 3. 默认三阶段

| 阶段 | 输入 | 输出 |
|---|---|---|
| 一：确认设计依据与约束 | 产品需求、业务链路、目标平台与参考 | 核心规则、来源与待确认项、实现范围与 Spec |
| 二：构建设计系统源码与 Gallery | 确认约束与当前资产需求 | 工程骨架、真实样式/组件、Gallery 与规范索引 |
| 三：复用设计系统搭建业务页面 | 真实设计资产与业务 Spec | 页面/路由/交互源码、Gallery 模式、验证与交付 |

只要求设计系统时完成前两阶段；完整业务需求必须继续第三阶段。阶段二可以从最小资产开始，后续页面所需组件与模式增量补齐，不提前搭建无关组件库。骨架、文档或 Gallery 完成不等于完整目标完成。

已有项目支持作为补充路径保留，按确认需求复用资产。Proposal 用于有分歧的视觉方向，完整规则巡检与独立任务管理按需调用，不扩展为默认全流程负担。

## 4. 为什么能提高稳定性

稳定性并不来自某个固定模型，而来自可检查的中间产物：

1. Adapter 固定项目上下文，减少重复理解造成的漂移。
2. Design System 把视觉判断转化为 tokens、组件和规则。
3. Spec 在写代码前固定范围、复用策略和验收标准。
4. Proposal 先缩小选择范围，再只渲染被选方案，降低无效生成。
5. 质量检查把“看起来完成”改为可验证的完成条件。

## 5. 运行资产

主流程不只依赖说明文字，还需要以下项目级产物：

- `RULES.md`：项目长期有效的强制约束和索引。
- `DEV-WORKFLOW.md`：不同需求类型在该项目中的具体落点。
- `.design-workflow/project-adapter.json`：技术栈、目录、命令和预览入口缓存。
- `.design-workflow/specs/*.md`：单次需求的技术方案与确认记录。
- `design-system/`：tokens、组件、页面、布局和交互规则，以及持续 Gallery 的入口与资产索引。
- 项目源码中的 Gallery：0-1 最小启动也需提供可运行展示，由宿主按项目技术栈实现；CLI 初始化的模板不等于展示站。
- `deliverables/`：检查结果与交付说明。

这些文件来自模板，但初始化后必须根据真实项目修改，不能把示例当成事实。

## 6. 默认完成判定

`.design-workflow/delivery.json` 记录确认范围、规则、源码/入口与验收条件。检查器核验必需产物、保守的相对引用、命令日志与浏览器/规则对照记录；当前源码或证据变化后重新验收。没有契约、源码或必需验证均不能返回完成。详见 [交付检查](delivery-contract.md)。

Skill 引导宿主执行，CI 使用退出状态实施门禁；两者的约束强度不同。程序判定只覆盖声明的输入和检查，不认证手工记录，也不自动证明视觉质量。

## 7. 局限性

- Adapter 可能过期，因此必须以源码和配置为准并定期核验。
- Design System 只能约束一致性，不能替代产品判断和用户研究。
- 多方案机制会增加前期时间，不适合明确且微小的修改。
- 预览不等于真实业务实现；数据、状态、异常和性能仍需单独验证。
- 流程卡点过多会降低小需求效率，应按风险设置轻量或完整模式。
