# 架构说明

## 1. Harness 与 Skills 的职责

| 层 | 解决的问题 | 典型输入 | 主要输出 |
|---|---|---|---|
| Harness | 哪些操作必须确定、可重复、可测试 | 代码仓库、CLI 参数 | 扫描结果、初始化文件、检查与诊断 |
| Workflow | 一次需求应按什么顺序完成 | 用户需求、代码仓库 | Adapter、方案 spec、实现、检查报告、交付记录 |
| Design System | 页面应遵循什么视觉与组件规则 | PRD、现有页面、截图、品牌信息 | tokens、布局、交互、组件和页面规范 |
| Proposal | 没有明确设计稿时如何选择方向 | 需求、设计系统、现有组件 | 方案摘要、选中方案预览、决策记录 |

`rules-governance` 位于检查层：它验证前三层产物是否保持一致，但不参与普通需求的方案决策。

```text
CLI Harness
├─ scan：只读识别项目
├─ init：非覆盖式创建运行资产
├─ check：确定性规则检查
└─ doctor：环境与状态诊断
        ↓ 提供事实与工具
Skills
├─ Workflow：编排
├─ Design System：设计约束
├─ Proposal：方案决策
└─ Rules Governance：语义审查
```

## 2. Project Adapter 的定位

Adapter 不是事实来源，而是项目事实的结构化索引：

- 事实来源：源码、配置、设计系统、规则文档和可执行命令。
- Adapter：记录这些事实在哪里、如何使用、最近一次核验时间。
- 主流程：先读 Adapter，再对关键字段做轻量核验；发现漂移时更新 Adapter。

它的价值不是让 Agent “第一次才能读懂项目”，而是减少每次重复扫描、降低遗漏，并让不同 Agent 使用同一套项目映射。

## 3. 条件调用

```text
先识别项目
  ├─ 0-1：建立骨架、最小规则、最小设计系统、Adapter
  └─ 已有项目：读取 Adapter，核验关键事实

再判断输入是否明确
  ├─ 有明确设计稿/截图/参考：直接形成实现 spec
  └─ 无明确视觉方向且有多种解法：调用 Proposal

实现过程中
  ├─ 缺少设计约束：调用 Design System Builder
  ├─ 已有约束：复用 tokens、组件和页面模式
  └─ 发现高影响变化：回写 spec 并请求确认

最后
  └─ 运行、交互、视觉一致性、影响范围、文档检查与交付沉淀
```

## 4. 为什么能提高稳定性

稳定性并不来自某个固定模型，而来自可检查的中间产物：

1. Adapter 固定项目上下文，减少重复理解造成的漂移。
2. Design System 把视觉判断转化为 tokens、组件和规则。
3. Spec 在写代码前固定范围、复用策略和验收标准。
4. Proposal 先缩小选择范围，再只渲染被选方案，降低无效生成。
5. 质量检查把“看起来完成”改为可验证的完成条件。

## 5. 运行资产

主流程不只依赖说明文字，还需要以下项目级产物：

- `RULES.md`：项目长期有效的强制约束和索引。
- `DEV-WORKFLOW.md`：不同需求类型在该项目中的具体落点。
- `.design-workflow/project-adapter.json`：技术栈、目录、命令和预览入口缓存。
- `.design-workflow/specs/*.md`：单次需求的技术方案与确认记录。
- `design-system/`：tokens、组件、页面、布局和交互规则。
- `deliverables/`：检查结果与交付说明。

这些文件来自模板，但初始化后必须根据真实项目修改，不能把示例当成事实。

## 6. 局限性

- Adapter 可能过期，因此必须以源码和配置为准并定期核验。
- Design System 只能约束一致性，不能替代产品判断和用户研究。
- 多方案机制会增加前期时间，不适合明确且微小的修改。
- 预览不等于真实业务实现；数据、状态、异常和性能仍需单独验证。
- 流程卡点过多会降低小需求效率，应按风险设置轻量或完整模式。
