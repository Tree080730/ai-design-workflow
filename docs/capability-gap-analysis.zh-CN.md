# Design Harness 能力与缺口分析

> 历史分析：本文写于宿主优先的产品定位确认之前。工具化建议不等于核心能力要求；当前产品定位、链路与能力状态以 [产品链路](product-flow.md) 为准，操作方式见 [宿主接入](host-integration.md)，token 导出和任务追踪属于可选增强。

评估日期：2026-10-03。基线：v0.1.2，提交 `2e31f41`。

本文基于当前源码、Skills、模板、测试，以及本次对话确认的产品目标。没有取得历史构建对话。本文是迭代讨论依据，建议尚未成为已批准的产品规格。

## 1. 产品目标与边界

已确认目标：帮助用户使用 AI 稳定开发符合规范、业务可用、支持后续页面与组件复用的界面。以 0→1 为主要入口，同时支持已有项目的 1→100。

创意生成不属于核心职责。Harness 需要把输入转成明确约束，使约束进入真实实现，验证结果，并在后续迭代中维护一致性。

“稳定”指约束、复用关系、业务行为和验证依据能够延续，不要求不同模型生成完全相同的源码。具体业务正确性仍需对应需求与验收依据。

“规范页面”目前没有单一固定定义。至少应区分：项目设计约束、通用界面质量、组件契约、业务状态与工程要求。项目中的具体阈值和适用规则仍需确认，不应凭空宣称符合某个行业标准。

## 2. 当前结论

仓库已有可运行的确定性工具和较完整的工作指引。最主要的缺口是：约束尚未可靠连接到运行代码，工作流要求尚未连接到可追踪的验证证据，后续复用尚未经过代表性场景评测。

现有 CLI 测试通过能证明所覆盖的工具行为，不能证明页面质量或 Agent 会遵循全部要求。Skills 中的要求属于执行指引，不能直接算作自动化能力。

## 3. 能力对照

| 能力 | 当前工具能力 | 当前指引 | 缺口与影响 |
|---|---|---|---|
| 项目识别 | 扫描依赖、scripts、固定候选目录、模式与框架信号 | 核验真实代码和命令 | 根级依赖与目录不足以覆盖 workspace、非标准目录；CLI 与 fallback 扫描口径不同 |
| 项目接入 | init 非覆盖式生成模板、刷新 Adapter | 0→1 建骨架，已有项目先读现状 | 没有安装成功后的完整使用样例，也没有确认约束已被 Agent 加载的证据 |
| 约束建立 | 复制 tokens、布局、交互与索引模板 | 按证据提取规则，未知项待确认 | 缺少可检查的规则状态、来源和必要项；占位文件可能被误当作准备完成 |
| 约束进入代码 | 提供静态 CSS 变量模板 | 要求唯一 token 入口与真实引用 | JSON 和 CSS 并列维护，无生成或一致性校验；init 不接入源码入口；排版 tokens 未导出到模板 CSS |
| 组件复用 | 部分目录发现、文档是否存在 | 先扫描复用面、说明新增理由 | 没有可靠的资产映射与使用证据；同名组件的文档映射可能冲突 |
| 任务约束 | 创建 specs 目录 | Spec 描述范围、复用、状态与验收 | 无任务状态、规则引用或执行证据的统一记录；中断后依赖人工重新理解 |
| 实现过程 | CLI 不生成业务代码 | 小步实现、共享影响分析 | 缺少让下一阶段发现偏离 Spec 或遗漏同步的机制 |
| 静态一致性 | 颜色正则与固定路径的文档存在检查 | 覆盖字体、间距、形状、动效等；语义判断与豁免 | 未检查未定义 token、token 漂移、文档内容、反向失效链接；颜色误报和漏报明显 |
| 渲染质量 | 无浏览器检查或证据收集能力 | 桌面与窄屏检查对齐、基线、等高、溢出 | 没有统一的页面/视口/状态/结果记录；静态检查不能证明渲染质量 |
| 业务可用性 | 发现常见测试目录 | 加载、空、错误、恢复、刷新、撤销与边界验证 | 不执行测试，不判断关键状态是否覆盖；发现目录不能证明链路通过 |
| 持续维护 | doctor 比对 Adapter 结构漂移 | 同步源码、文档、索引和预览 | 不检查设计资产内容漂移，也没有共享组件改动后的消费页面验证记录 |
| 交付与恢复 | JSON 输出、部分退出码 | 检查与交付模板，区分未验证风险 | 无证据时仍只能靠 Agent 自报；交付目录在架构、示例与 gitignore 中不统一 |
| 真实效果评测 | 9 项 CLI 测试和简单 React 示例 | 暂无完整评测流程 | 缺少首页面→第二页面→共享组件修改的验证场景，无法衡量持续一致性 |

主要依据：`packages/cli/src/{scan,init,check,doctor}.mjs`、四个 `skills/*/SKILL.md`、Workflow references、CLI templates、`test/cli.test.mjs`。

## 4. 已核实的具体断点

### 4.1 初始化完成与可开发就绪没有分开

在临时空目录运行 init 后，doctor 所有项目均 pass，check 返回零问题，但布局仍含待确认占位项，没有业务页面，也没有 token 源码接入。这是工具当前定义的结构健康，不是页面开发准备完成。

建议保留结构诊断，并额外区分：结构已建立、必要约束待补充、约束已接入、当前任务待验证。旧命令的 healthy 语义需要谨慎兼容，不宜直接改变后让已有调用失效。

### 4.2 配置生成了，检查尚未消费

init 写入 `strictChecks` 和 `designSystemDirectory`，当前 scan/check/doctor 没有读取配置来驱动行为。check 固定查找 `design-system/components` 与 `design-system/pages`，即使用户指定其他目录也不生效。

临时夹具中指定 `docs/design-system`，并放置对应组件文档，check 仍报告默认目录缺失文档。该问题应先于扩大检查规则解决。

### 4.3 正则候选与规范违例混在一起

临时夹具中的注释 `// reference color #123456` 被报为 P1；同文件中的未定义变量 `var(--color-does-not-exist)` 和 `padding: '37px'` 未报告。

颜色扫描应清楚表达候选与确定违例的区别。局部间距是否违规需要项目规则依据，不能一律禁止。无明确来源的严重级别不能替代语义判断。

### 4.4 Adapter 声明与实际使用没有贯通

React + Vite 识别在 scan 中硬编码，`adapters/react-vite.json` 尚未被加载；扫描发现的设计系统目录也没有贯通到 check。Fallback scanner 使用另一套模式与包管理器判断。

建议先统一项目事实模型与路径解析，再选择适配器扩展方式，避免维护多份并不一致的事实。

### 4.5 设计资产缺少单一可执行来源

JSON tokens 与 CSS tokens 是两份静态模板。修改前者不保证后者变化；模板 CSS 没有包含 typography.json 定义。Skill 要求唯一来源，但工具尚未验证这种关系。

对新项目可选择一种生成或校验方式。对已有项目应认可其现有 token 工具链并建立映射，不强迫迁移到 Harness 自有格式。

### 4.6 完整性与低摩擦使用需要协调

Workflow 对所有写入任务要求 Spec 与确认，Proposal 对无明确设计输入的新增页面要求方案选择；RULES 模板则强调高影响变更确认。两者粒度需要统一。

Proposal 可以保留为处理结构或交互分歧的条件工具，但不应成为每次页面开发的创意入口。没有品牌输入时，应区分可采用的工程基线、待确认视觉选择和阻塞业务决策，避免反复追问或暗自定案。

## 5. 建议打通的第一条完整链路

这是待讨论的验证场景，不要求将其业务内容固化为产品功能。

选择一个边界明确的 React + Vite 两页面应用，具备共享布局、按钮与反馈模式，以及一个可复现的异步业务流程。

| 步骤 | 输入 | 必须留下的输出 | 完成条件 |
|---|---|---|---|
| 接入 | 空仓库或最小业务骨架、目标技术栈 | 项目事实与可运行入口 | 命令和目录真实可用 |
| 建立约束 | 页面需求、提供的设计依据、允许采用的基线 | 必要 tokens、布局、交互、约束来源与未知项 | 阻塞项明确；必要约束落实到源码 |
| 首页面开发 | 任务范围与验收条件 | 页面、首批共享组件、最小资产映射 | 构建通过，适用状态可操作 |
| 验证修正 | 路由、状态、代表性桌面与窄屏 | 检查结果、实际渲染与交互证据、修正记录 | 确定违例修复，未验证项明确 |
| 第二页面开发 | 新需求、已有规范与组件 | 复用关系、必要扩展及理由 | 不重复创建语义相同资产；一致性有证据 |
| 共享资产变更 | 一个共享组件或 token 的修改 | 受影响页面清单与验证结果 | 两页面保持契约，无遗漏同步 |
| 恢复与交付 | 中断后的新会话 | 当前任务、已完成工作、失败与待验证项 | 能沿已有记录继续工作，不宣称未执行检查通过 |

两页面及共享变更是必要评测内容：单个漂亮首屏无法验证复用或持续一致性。

## 6. 建议的迭代顺序

| 轮次 | 重点 | 验收依据 |
|---|---|---|
| 第一轮：统一事实与就绪语义 | 配置生效、路径解析一致、清楚区分初始化与约束就绪、fallback 口径统一 | 自定义目录有效；占位模板不会被描述为规范完备；已有行为兼容 |
| 第二轮：让约束进入运行代码 | 明确 token 来源与映射、验证引用和导出、建立轻量组件/页面映射 | token 变化反映到实现；缺失引用能发现；已有工具链可保留 |
| 第三轮：闭合验证与恢复 | 按风险记录任务验收、执行结果与证据，明确失败和未执行状态 | 静态、渲染、交互验证可追踪；中断后可恢复；无证据不算通过 |
| 第四轮：真实链路评测 | 两页面开发、共享资产变更、已有项目接入 | 评测中发现的问题回归到工具、Skills 与测试，而非只补说明 |

完整链路评测应从前期就建立夹具，随各轮演进；第四轮集中评估效果，不应等到最后才试用。

暂不建议先扩大框架数量、引入创意生成或批量生成组件文档。优先让一条链路真实闭合，再扩展覆盖面。

## 7. 后续共同确认的事项

1. 无品牌或设计参考时，允许 Harness 使用哪些明确标记的基础规则，哪些必须由用户决定？
2. 首条链路采用的业务场景与实际验收标准是什么？
3. 哪些结果必须阻止交付，哪些可记录为风险或明确不适用？
4. 用户已有的授权如何沿任务延续，哪些变化才需要再次确认？
5. 约束、任务与验证证据采用哪些最小记录方式？先定义内容，再决定格式和新命令。

这些是产品与使用链路决策，本报告不擅自将建议写成强制规则。
